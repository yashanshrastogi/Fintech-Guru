# Fintech Guru V2 — Final Truth Audit

## 1. Internal Consistency vs. Real-World Accuracy

### Initial Fallacy
In our previous evaluation, we reported a "100% accuracy" rate. This was an **internal consistency** artifact. The holdout dataset was synthetically generated by our own system, making the evaluation circular. Furthermore, that pipeline had a 100% Fallback Rate, meaning it completely ignored the LLM component.

### The Truth Audit Solution
To measure true performance, we authored an **independent, manually generated External Benchmark** consisting of 100 edge-cases designed to trick naive heuristics. The benchmark focuses on real-world capabilities:
1. **Forward-looking Income Scaling**: (e.g., "Salary increased from $5000 to $7000"). The LLM must override the historical transaction record and inject the new projected income.
2. **Behavioral Cancellations**: (e.g., "I am cancelling my gym subscription"). The LLM must find and drop the recurring expense before it triggers a safety violation.
3. **Optimized Payment Plans**: Deterministic boundaries where the user can afford an item via installments over 3 months, but would violate safety boundaries if paid in full today.

## 2. LLM Integration & Deterministic Fallback

The system now enforces a strict **Multi-Agent Pipeline** architecture:
`User Input -> Evidence Extraction (Qwen) -> Canonical State Reconciliation -> Deterministic Cashflow Simulator -> Optimization Engine`.

### Qwen Evidence Extraction
The system now hits an external LLM server (mocked currently, representing Ollama `qwen2.5:8b`). It extracts:
- `extracted_salary`: Overriding future expected income logic.
- `cancellation_request`: Specific categories to drop from the recurring simulator.

### Deterministic State Boundary
Evidence from Qwen is no longer arbitrarily modifying raw transactions. Instead, it passes through `evidence_overrides` directly into `FinancialState`. The deterministic `simulate_cashflow` ledger relies entirely on this unified state matrix to ensure zero mathematical errors.

### Graceful Degradation
If the LLM is down, offline, or returns a 500, the system gracefully degrades. It traps the `ConnectionError`, logs a warning, returns an empty evidence dictionary, and relies strictly on the conservative historical deterministic engine.

## 4. Architectural Fixes Discovered During Audit

During the audit, we uncovered and resolved severe foundational issues that were previously hidden:

1. **Pydantic Type Dropping**: The `transactions` list was typed as `List[BaseEvent]`. Pydantic was silently dropping the `event_type` ("income" vs "expense") field, forcing the system to assume everything was an expense. We added `event_type` to `BaseEvent`.
2. **Double-Counting Recurring Income**: The simulator was incorrectly applying historical one-off events and future recurring projections on the same ledger day, artificially inflating balances. 
3. **Hardcoded Mock States**: The canonical state builder was completely ignoring the user's actual profile balance and hardcoding `10000.0`. It now dynamically parses `current_available_balance` from the `UserProfile`.
4. **Indiscriminate Cancellation**: The system was overriding the extracted cancellation category incorrectly in a loop, applying only the last category (Netflix) instead of aggregating a list of cancelled categories (Gym and Netflix). It now uses a `cancelled_categories` array to prune the simulator safely.
